# Kubernetes RBAC feasibility

**Status: source-only exploration, 2026-11-01. No Kubernetes connector is
implemented.** Kong remains Soundcheck's only supported target. This advances
the [connector shortlist](connector-selection.md) with a proposed boundary and
acceptance example; it does not establish user demand or deployment readiness.

The research target is **Kubernetes v1.34.0**, an available fixed release chosen
for source inspection, not a claim about the latest release. Links below pin
the implementation to that tag. No Kubernetes process, upstream authorizer,
cluster, or new SMT model was executed. `go` was unavailable in the local
environment; no toolchain was installed. All example decisions below are
source-derived expectations, not conformance results.

## Finding: feasible for static grants, with a narrower claim

A useful first question is: **does the complete RBAC snapshot grant the fixed
workload its required API access, without granting the forbidden access?**
That fits a paired frozen requirement. It does not establish that a workload
can successfully execute an operation or can never gain additional privileges.

For an already authenticated request, RBAC grants access if any applicable
bound rule matches. Resource-rule matching combines verb, API group,
resource/subresource and object name. There is no rule priority or explicit
negative rule. Critically, the upstream authorizer returns `Allow` for a grant
and **`NoOpinion`** otherwise. This is a claim about the RBAC component, not the
whole API server. See the pinned [RBAC authorizer](https://github.com/kubernetes/kubernetes/blob/v1.34.0/plugin/pkg/auth/authorizer/rbac/rbac.go).

The authorization chain stops at its first `Allow` or `Deny`; `NoOpinion`
continues to another authorizer. An earlier webhook denial can prevent a
request that RBAC would allow, and another authorizer can allow one RBAC does
not grant. The server also installs a privileged-group authorizer before the
configured chain. Therefore even an otherwise RBAC-only deployment needs the
`system:masters` bypass accounted for. Sources: [chain composition](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/apiserver/pkg/authorization/union/union.go),
[authorizer construction](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/kubeapiserver/authorizer/reload.go).

The initial output should say **RBAC grant / no RBAC grant**. Translating the
latter into end-to-end denial requires a separate, reviewed closure assumption
about authentication, privileged identities and the entire authorizer chain.
Likewise, an authorization grant does not establish object existence,
admission acceptance or successful execution. [Kubernetes authorization](https://kubernetes.io/docs/reference/access-authn-authz/authorization/)
separates admission from authorization.

## What a complete input must contain

The rule resolver considers all ClusterRoleBindings and, for a nonempty request
namespace, RoleBindings in that namespace. A RoleBinding can reference a local
Role or a ClusterRole, but grants only in its own namespace. A
ClusterRoleBinding grants its ClusterRole without that namespace restriction.
Subjects match exact usernames, supplied group membership, or a service-account
username. A service-account subject without a namespace uses the RoleBinding's
namespace; an unqualified service account in a ClusterRoleBinding cannot match.
See the pinned [rule resolver](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/registry/rbac/validation/rule.go).

Consequently, the proposed input is a **complete effective snapshot plus trusted
identity and scope assumptions**, not an isolated Role or a PR's changed YAML:

- Include every ClusterRoleBinding, every RoleBinding in the request-domain
  namespaces, and all referenced Roles/ClusterRoles. A domain covering arbitrary
  namespaces needs bindings across all namespaces. Include default bindings and
  grants to broad groups, not just grants naming the workload directly.
- Freeze username and complete group membership outside the repair loop.
  Standard service-account usernames and namespace groups are generated by
  [service-account identity helpers](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/apiserver/pkg/authentication/serviceaccount/util.go);
  the authentication wrapper can add
  [`system:authenticated`](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/apiserver/pkg/authentication/group/authenticated_group_adder.go).
  Removing a group from the verification input must not count as a repair.
- Record snapshot provenance and assumed stability. A file cannot prove that
  an export omitted no binding, or that different object lists were captured
  without intervening policy changes. Candidate edits must be applied to that
  complete baseline, with untouched objects retained.
- Reject unresolved references and unsupported applicable semantics in the
  first prototype. This is intentionally stricter than the upstream resolver's
  ability to continue after a lookup error; missing input must not become a
  denial proof.

Aggregation is a separate controller computation: selectors choose
ClusterRoles and the controller rewrites the aggregate's rules. The first
prototype should reject aggregation rather than predict convergence from
manifests. A later effective-snapshot mode would need to state exactly which
materialized rules it checks and for what instant. See the
[aggregation controller](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/controller/clusterroleaggregation/clusterroleaggregation_controller.go).
Default roles/bindings are also reconciled on server startup; checking an
edited default object is not a guarantee that its permissions stay removed.
See [v1.34 default RBAC reconciliation](https://v1-34.docs.kubernetes.io/docs/reference/access-authn-authz/rbac/#auto-reconciliation).

## Initial subset and edges to preserve

The recommended first prototype checks **namespaced, named `get` requests for
core `configmaps` and `secrets`**, against explicit, nonaggregated
`rbac.authorization.k8s.io/v1` objects. Support User, Group and ServiceAccount
subjects, both binding kinds, literal names, and the standard `*` match for
verbs, API groups and resources. An applicable broad grant must be matched or
reported unsupported, never silently dropped. This deliberately small request
domain avoids implying all Kubernetes API operations are supported.

| Semantic edge | Finding and proposed treatment |
| --- | --- |
| API group and resource | Keep both: `""` is the core group; resource names are API plurals, not object kinds. API version is not an RBAC rule discriminator. |
| Namespace and request scope | `namespace=""` includes all-namespaces collection requests, not a wildcard that combines RoleBinding grants from each namespace. The resolver skips namespaced RoleBindings for such requests. The first subset requires a nonempty namespace. |
| Object names | Empty `resourceNames` means unrestricted; entries match exactly. A literal `"*"` in `resourceNames` is not the wildcard used by `resources`. Support named `get` first. |
| Subresources | `pods` and `pods/log` differ. The matcher accepts `*/log`; it does not treat `pods/*` as a general subresource glob. Defer subresource request support, retaining broad-resource grants that match the initial domain. |
| Non-resource URLs | Separate request kind, with exact or trailing-`*` prefix matching. Defer these requests; do not reinterpret URLs as resource names. |
| Collection requests | A name-restricted list/watch needs the request's exact `metadata.name` selector reflected in its authorization attributes. Top-level create and deletecollection do not obtain the object's name from its body. Defer HTTP-to-request translation and these verbs. |
| Unknown or invalid fields | Validate/default the RBAC API objects before matching. Reject unsupported semantic fields; do not use permissive YAML parsing as a validity check. |

Matching details come from the pinned [matching helpers](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/apis/rbac/v1/evaluation_helpers.go)
and [RBAC API types](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/api/rbac/v1/types.go).
HTTP verbs, names and selectors are translated by the separate
[request-info parser](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/apiserver/pkg/endpoints/request/requestinfo.go).
Object validation has its own [upstream implementation](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/apis/rbac/validation/validation.go).
Rules demonstrably disjoint from the explicit request domain need not widen
that domain; any such exclusion needs an auditable justification.

`bind` and `escalate` are additional authorization checks associated with RBAC
mutations, not ordinary negative policy rules. A static decision for one request
does not model the resulting policy transition. See [escalation/binding checks](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/registry/rbac/escalation_check.go).
Impersonation separately authorizes changes to the request identity before
subsequent processing; see the [impersonation filter](https://github.com/kubernetes/kubernetes/blob/v1.34.0/staging/src/k8s.io/apiserver/pkg/endpoints/filters/impersonation.go).
Neither mechanism, nor chains involving workload creation or credentials, is
covered by the proposed one-request grant claim. **Do not market this subset as
privilege-escalation prevention or full tenant isolation.**

## Concrete paired requirement and repair example

This is a synthetic specification, **not a supported Soundcheck contract
format**. Assume a closed, static RBAC snapshot containing exactly the objects
below, with no default or external grants. This assumption is useful for a
local experiment; it is not a claim about a normal cluster.

Freeze the workload identity as
`system:serviceaccount:team-a:reconciler`, with groups
`system:serviceaccounts`, `system:serviceaccounts:team-a` and
`system:authenticated`. Its requirement, quantified over valid named requests:

- **Required grant:** `get` on core `configmaps` in `team-a`, for every name.
- **Forbidden grant:** the same identity's `get` on core `configmaps` in every
  other nonempty namespace, for every name.
- **Approved repair scope:** only that identity's foreign-namespace ConfigMap
  grants may change. Preserve grant decisions for all other requests in the
  declared model domain, including its own-namespace reads and other subjects.

Define a ClusterRole named `config-reader` with this complete rule:

```yaml
apiGroups: [""]
resources: ["configmaps"]
verbs: ["get"]
```

Keep a separate RoleBinding `ops/health-read` referencing `config-reader`, with
User subject `health-check`. Its identity has group `system:authenticated`.
The three candidate states differ only in the workload binding:

| Candidate | Workload binding | Workload: `get team-a/configmaps/settings` | Workload: `get team-b/configmaps/settings` | `health-check`: `get ops/configmaps/health` |
| --- | --- | --- | --- | --- |
| Unsafe | ClusterRoleBinding `worker-read`: ServiceAccount `team-a/reconciler` → `config-reader` | Grant | Grant: violates prohibition | Grant |
| Deny-all repair for workload | Remove `worker-read`; retain `ops/health-read` | No grant: violates required access | No grant | Grant |
| Valid static repair | Replace the ClusterRoleBinding with RoleBinding `team-a/worker-read`, same subject and roleRef | Grant | No grant | Grant |

For both binding kinds, the roleRef is
`{apiGroup: rbac.authorization.k8s.io, kind: ClusterRole, name: config-reader}`.
The service-account subject's namespace remains `team-a`; the RoleBinding's
namespace controls where the grant applies. Replacing the binding means
removing the ClusterRoleBinding, not adding a RoleBinding alongside it.

This example distinguishes security from required functionality without an
explicit RBAC deny rule. The table is representative; checking its three
requests alone would not prove the quantified contract or preservation.
Preservation requires comparing the complete before/after grant functions
outside the approved scope. The proposed valid repair changes only the direct
workload grant in foreign namespaces under these closed-world assumptions.

## Shared-core impact and an independent oracle

The present [IR](../../core/ir.ml) has an authenticated name in its OCaml type,
but its conditions distinguish only anonymous/authenticated; the
[SMT encoder](../../core/smt_encode.ml) declares `is_anon`, and the
[witness layer](../../core/witness.ml) reconstructs an arbitrary authenticated
subject. That cannot distinguish Kubernetes users or group membership.

An implementation would need genuine identity equality/group-membership
predicates and separate API group, resource, namespace and name attributes.
Verb can reuse the action concept, while Kubernetes lowering must use API verbs
such as `get`, not HTTP `GET`. Later subresources and non-resource requests need
their own representation. Counterexamples, witness validation, frozen contracts
and report schemas must carry the same distinctions; storing namespace in Kong's
host or encoding identities as HTTP headers would hide semantics.

For exact supported rules, additive grants appear compatible with existing
equal-priority Allow rules **if the entire grant condition is in the complete
match and guards are true**. The solver process and obligation machinery should
be reusable. This is a design inference, not an implemented or tested lowering.
An internal Boolean absence-of-grant must retain the RBAC-specific meaning at
the reporting boundary; modeling the full authorizer chain would be a separate
tri-state/composition task.

The next independent oracle should execute upstream code in a disposable
v1.34.0 checkout, using its matching staging dependencies and toolchain
requirements from [go.mod](https://github.com/kubernetes/kubernetes/blob/v1.34.0/go.mod):

1. Decode/default/validate the synthetic objects independently of Soundcheck.
   Populate upstream static role getters/listers;
   `NewTestRuleResolver` exposes a `StaticRoles` implementing all four required
   interfaces.
2. Call production `rbac.New(roles, bindings, clusterRoles, clusterBindings)`
   and `Authorize` with explicit `user.DefaultInfo` and
   `authorizer.AttributesRecord`. This exercises binding resolution as well as
   rule matching; calling a copied `RuleAllows` function alone would not.
3. Record `Allow`/`NoOpinion`, reasons and resolution diagnostics separately.
   Check both namespaces, a third namespace, other users, group-only grants,
   overlapping grants, binding scope, restricted names and missing references.
   Mutation controls must show that retaining the original ClusterRoleBinding
   still grants foreign access, and deleting every grant breaks required access.
4. Only after the reference harness passes should an OCaml prototype be compared
   against it. Test rejected boundaries separately. Record the resolved upstream
   commit, harness digest, toolchain and fixture hashes with results. A finite
   oracle matrix tests agreement on its cases; it is not proof of all lowering.

The constructor and static interfaces are available in the source-linked
authorizer and resolver above. This oracle needs no cluster or credentials and
would be a research/development dependency, not a Go runtime shipped with
Soundcheck. **It has not been built or run in this exploration.**

## Recommended next decision

Retain Kubernetes RBAC as the leading feasibility candidate. Before committing
to delivery, build the small upstream oracle and obtain an owner-reviewed,
authorized complete snapshot with independently stated paired requirements.
Measure how much of it the proposed subset accepts, especially aggregation and
default/group grants, and review the identity/request-model change together
with its report and contract implications. If closure or input coverage is poor,
revisit the subset before implementing a connector. Continue shipping Kong
coverage meanwhile; no Kubernetes capability or delivery date follows from this
source study.

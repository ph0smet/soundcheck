# Contributing to Soundcheck

Thanks for helping improve Soundcheck. Focused bug reports, formalizable feature
proposals, documentation fixes, and well-tested implementation changes are
welcome.

Soundcheck's central obligation is no false proof within its supported model and
assumptions. Unsupported target behavior must fail closed; a passing test suite
does not justify weakening a contract, expected result, or assurance claim.

## Before you start

- Search the [existing issues](https://github.com/ph0smet/soundcheck/issues) and
  the [roadmap](README.md#roadmap).
- Use the repository's structured bug-report or feature-request form when
  [opening an issue](https://github.com/ph0smet/soundcheck/issues/new/choose).
- Open an issue before changing target semantics, the shared decision IR, frozen
  contract formats, or stable public result schemas.
- Describe verification features as a precise decision question. If the
  intended property cannot be formalized, it is not a good fit for Soundcheck.
- Sanitize all examples. Never post credentials, production configurations,
  evidence bundles, customer identifiers, or confidential counterexamples.

Coding agents must also follow [AGENTS.md](AGENTS.md). That file contains
agent-specific working guidance; this document is the contributor-facing entry
point.

## Development setup

Follow the [getting-started guide](docs/getting-started.md) to install OCaml,
Dune, the `yaml` package, and Z3.

```sh
eval "$(opam env)"
opam install . --deps-only --with-test
dune build @all
```

The project requires OCaml 5.0 or newer and Dune 3.11 or newer. Z3 4.16.0 is the
regression-tested solver baseline, and the regression gate also requires `jq`.
Edit dependency metadata in `dune-project`; `soundcheck.opam` is generated by
Dune.

## Keep changes focused

- Work on a `feat/`, `fix/`, `docs/`, or `chore/` branch.
- Preserve unrelated changes.
- Keep generic decision, property, solver, witness, reporting, and evidence
  logic in `core/`.
- Keep target parsing, semantic lowering, assurance assessment, and
  counterexample lifting in the connector.
- Keep CLI, MCP, CI, and future HTTP adapters thin.
- Reject unsupported semantics explicitly. Never silently under-approximate a
  safety question or use uncertain enforcement to prove functionality.
- Treat frozen contracts and public schemas as reviewed interfaces. Do not
  change their meaning merely to make a fixture pass.

Substantial semantic work may need a concise accepted plan under `docs/plans/`.
Routine documentation and maintenance changes do not.

## Add evidence that matches the claim

A semantic change needs an independently justified target expectation and a
regression that would fail for the relevant wrong implementation. Agreement
between two readers of Soundcheck's own IR is useful, but is not independent
Kong conformance evidence.

Do not regenerate expected results from the implementation under test. Keep
conservative and unsupported boundaries visible.

## Run the checks

For every change:

```sh
eval "$(opam env)"
bash scripts/check.sh fast
```

For changes to Kong semantics or the conformance harness, also run the pinned
target checks when Docker, a running daemon, and `curl` are available:

```sh
eval "$(opam env)"
bash scripts/check.sh full
```

The full command serializes the regression suite and real-Kong conformance.
Run only one Kong conformance harness at a time on a host because its containers and
ports are shared.

For RBAC semantics or shared identity/object-model changes, also run the
[pinned Kubernetes authorizer comparison](bench/kubernetes-rbac/conformance/README.md):

```sh
bash bench/kubernetes-rbac/conformance/run.sh
```

This separate command requires Go and Python 3.11 or newer, verifies pinned
module downloads, and records reference comparisons under `_build`. Ordinary
`dune test` does not require Go, network access, or a Kubernetes cluster.

After committing, maintainers can validate the exact revision in a clean
throwaway worktree:

```sh
bash scripts/check-commit.sh HEAD
```

That check does not run Docker and does not validate uncommitted edits.

## Open a pull request

Keep the description concise and include:

- the behavior that changed;
- why the change is sound within the declared model;
- checks actually run and their results;
- checks skipped or blocked, with the reason;
- independently justified target evidence for semantic changes; and
- any unresolved scope or semantic decision.

Do not include AI attribution, generated-by notices, or co-author trailers unless
the project owner explicitly requests them.
